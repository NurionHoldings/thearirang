# 아리랑마켓 계약·정산 업무실

입점업체/플랫폼 운영자 업무 화면의 **계약·전자서명 · 정산·지급요청 업무실** 링크 또는 `/partner-finance.html`에서 이용한다. 기존 `__Host-arirang_market` HttpOnly 세션과 계정 권한을 사용한다. 새 비밀번호 환경변수는 필요 없다. 건물 총괄·층별·자료업로드 관리자의 권한을 부여하지 않는다.

## 계약 제공과 전자서명

1. 운영자가 업체, 사업자 상호/대표/등록번호, 운영자 서명자, 기간, 합의 요율(bp), 수수료 부가세, 정산 검토 주기, 특약을 입력한다. 기본 요율을 추정하거나 임의로 채우지 않는다.
2. 서버가 생성한 **계약 전문 미리보기**를 읽고 운영자 동의로 발행한다. 미리보기와 발행 시 문서 해시가 일치해야 한다. 발행 당시 업체명·주소와 계약 조건을 스냅샷으로 저장한다.
3. 해당 업체 계정만 계약 전문을 열람하고, 유효기간 30분의 계정/문서 해시 연결 열람 토큰을 받는다. 업체가 전문·전자계약 방식 및 대표/위임 권한에 동의하고, 서명자 성명과 현재 계정 비밀번호를 재입력한다. 비밀번호는 기존 계정 검증기로 확인하고 저장/기록/AI 전달하지 않는다.
4. 서버는 열람 토큰·계정·문서 해시·계약 상태를 확인한 뒤 1회 서명을 기록한다. 이 절차는 실제 읽음/대표 권한의 외부 신원확인을 보증하지 않는다. 공동인증서·신원인증사업자 연동이나 공인전자문서센터 보관 기능은 아니다.
5. 문서 JSON과 서명이력을 다운로드하고, 동일 전문을 출력하거나 브라우저의 PDF 저장 기능을 이용한다. 열람 토큰은 다운로드에서 제외한다. 서명 시각·계정·동의 방식·SHA-256 및 발행/열람/서명 이력을 보존한다.
6. 계약의 JSONB 키 순서에 영향을 받지 않는 정렬된 canonical JSON SHA-256을 사용한다. 서명 원본은 DB 트리거에서도 수정/삭제를 거부한다. 미서명 계약은 발행 철회 후 재발행할 수 있다. 서명 후 갱신은 기존 기간과 겹치지 않는 새 계약과 재동의가 필요하다. 중도 합의해지/중도 요율 변경 절차는 별도 확장이 필요하며 원본을 덮어쓰지 않는다.

## 계산 규칙

- 상품 카드 매출만 대상으로 한다. 배송비/외부 배달대행료/그 밖의 비용은 이 원장에 포함시키지 않는다.
- 플랫폼 이용료 = 상품 결제액 × 플랫폼 bp / 10000, 결제 서비스 수수료 = 상품 결제액 × 결제 bp / 10000.
- 각 수수료를 원 단위 반올림하고, 합계에 계약 부가세 bp를 적용해 다시 반올림한다. BigInt 정수 연산으로 계산한다.
- 정산액 = 상품 매출 - 플랫폼 이용료 - 결제수수료 - 수수료 부가세.
- 결제수수료는 계약 약정 요율이며 PG 실비 자동 전가 모델이 아니다. PG 명세 실비와 약정 공제액의 차이를 명시한다. 차이 사유가 없으면 승인이 차단된다.
- 예: 100,000원 / 플랫폼 5% / 결제 3% / 수수료 부가세 10% → 5,000원 + 3,000원 + 800원 공제 → 91,200원. 이는 설명용이며 실제 계약 기본값이 아니다.
- 부분환불은 **원 결제 수수료 × 누적 환불액 / 원 결제액**의 전후 반올림 차액을 반영한다. 여러 번 나누어 전액 환불해도 원 공제액이 정확히 상쇄된다. 중복 참조번호·다른 업체 원 결제·초과 환불·미래 거래·계약 전 거래는 거부한다.

## 원장과 보완

현재 카드 PG와 외부 배달대행은 미연동이다. 자동 매출 수집/정산/은행 송금 완료로 표시하지 않는다. PG 명세·환불 영수증의 상품액·일시·실비를 운영자가 대조한 후 거래 고유번호와 증빙 문서번호/보관 위치를 입력한다. 이 증빙 필드는 원문 업로드나 PG 서버 검증이 아닌 **수동 대조 참조**다. 실물 명세/영수증 원본은 별도 안전한 저장소에 보관해야 한다. 소비자 주문의 기존 결제 상태와 COD 제한을 변경하지 않는다.

PG 실비 전사 오류나 차액 설명을 보완할 때는 **PG 대조 보완**에서 정정 실비·사유·증빙 참조를 추가한다. 원 거래/감사 이력은 덮어쓰지 않는다. 정산에 포함한 거래는 초안을 해제한 뒤 보완한다. 이미 지급한 원장은 과거 금액을 바꾸지 않는다. 실제 환불은 새 환불 거래로 다음 정산에 반영한다. **전사 오류 반제**는 실제 고객 환불과 구분된 정정 전표다. 정산에 배정되지 않은 원 전표에만 반대 금액 전표를 추가하며, 이미 반제한 전표/반제 자체/지급 완료 전표는 반제할 수 없다. 환불이 연결된 매출은 환불 전표부터 확인한다. 잘못 옮긴 금액을 상쇄한 후 정확한 PG 증빙으로 새 고유번호(예: 원 PG번호:정정1)의 매출을 재등록한다. 원문 증빙과 원 전표·반제·재등록 관계를 감사 이력에 남기며 실제 고객 환불로 표시하지 않는다.

## 정산·승인·지급요청

1. 업체와 한국시간 마감 시각을 지정해 전체 미정산 원장에서 초안을 만든다. 화면 원장 표시 300건 제한은 계산 대상 제한이 아니다. 정산 1건은 최대 2,000거래이며 업체별 진행 중 초안/승인/지급요청은 하나다. 이미 배정한 거래는 UNIQUE 키로 중복 정산을 막는다.
2. 원장 검증은 계약 상태/해시, 스냅샷 해시, 원장 대조, PG 실비 차이 사유, 추가 미정산 거래·환불, 양수 지급액을 검사한다. 금액 스냅샷은 DB에서도 수정/삭제할 수 없다.
3. 검증을 실행하고 통과한 뒤 관리자가 승인한다. 상태 변경에는 버전 검사를 사용한다. PG 보완/새 환불이 있으면 초안 해제 후 다시 산출한다. 승인 후 환불은 승인을 해제하며, 요청 후 환불은 지급 확인 전에 회수·재산출을 요구한다.
4. 관리자가 별도로 확인한 은행/계좌/예금주/예정일/메모를 입력해 고유 지급요청서를 생성한다. JSON 내역·출력/PDF·지급요청 HTML 저장을 제공한다. **지급요청 생성은 내부 요청 기록과 파일 생성이며 금융기관/다른 사람에게 전송하거나 이체하지 않는다.**
5. 실제 은행거래를 대조한 관리자가 이체 증빙번호와 확인으로 지급 완료를 기록한다. 은행 API 검증은 아니다. 지급 전 보완이 생기면 요청 회수 후 다시 진행한다. 이미 지급한 거래의 환불은 다음 양수 매출과 상계하고, 음수 배치만으로 지급요청을 만들지 않는다.
6. 계약의 정산 검토 주기는 합의 조건으로 저장된다. 자동 은행 지급·자동 정산 일정 실행은 포함하지 않으며 운영자가 마감 시각/예정일을 지정한다.

## 아르카온

계약 카드의 **아르카온 계약 검토**, 정산 카드의 **아르카온에게 검토 요청**으로 문답한다. 계약 조항·기간·요율·계산 예제, 또는 선택 정산의 서버 검증·합계·상태만 사용하며 수취계좌·계약 당사자의 사업자번호·주소는 AI 컨텍스트에서 제외한다. 사용자가 대화창에 입력한 내용은 전달되므로 비밀번호/계좌를 입력하지 않는다.

기존 `consultEthernion`을 재사용해 아르카온 초안 → API 보완 검토 → 최종 답변을 SSE로 진행한다. 실제 ChatGPT 대화와 연결했다고 주장하지 않는다. 기존 AI 설정이 없으면 서버 검증 안내만 제공한다. 모델 연결 실패를 검토 완료로 표시하지 않는다. AI는 금액·계약 수정, 승인, 지급요청 생성, 송금 도구를 갖지 않는다. 화면 작업을 통해 관리자가 확인한다.

## 배포·검증

새 자동 적용 migration: `20261102090000_market_contract_settlements.sql`. 기존 적용 migration과 주문 테이블을 수정하지 않는다. DB 연결 정보/비밀번호는 읽거나 공개하지 않는다. 공개자료 출력 카탈로그에는 사적 계약·정산서를 추가하지 않는다.

검증: PGlite 실제 migration/트랜잭션과 HTTP 권한 테스트, JSDOM 열람·서명·출력·문답 테스트, 기존 마켓/건물 전체 테스트, 빌드·TypeScript 검사. 실제 업체 계약 체결·PG 거래·은행 이체·유료 AI 호출은 테스트를 위해 실행하지 않는다.
